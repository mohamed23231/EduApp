# Expo Configuration Rules

## Managed workflow — don't touch native folders

`android/` and `ios/` are **generated by Expo prebuild**. Editing them directly is forbidden because the next prebuild wipes the changes.

- ✅ Add a config plugin under `plugins/` and register it in `app.config.ts`.
- ✅ Modify `app.config.ts` for permissions, plugin order, deep link schemes.
- ❌ Hand-edit `android/app/build.gradle`, `ios/Podfile`, `AndroidManifest.xml`, etc.
- ❌ `expo prebuild --clean` without confirming with the user (the safety hook blocks this).

## Config plugin pattern

```ts
// plugins/withCustomManifestEntry.ts
import { withAndroidManifest, ConfigPlugin } from '@expo/config-plugins';

export const withCustomManifestEntry: ConfigPlugin = (config) => {
  return withAndroidManifest(config, (cfg) => {
    // mutate cfg.modResults safely
    return cfg;
  });
};
```

Register in `app.config.ts`:

```ts
plugins: [
  // ...other plugins
  './plugins/withCustomManifestEntry',
],
```

## google-services.json placement

`google-services.json` MUST live at the **project root**, not `android/app/`. Expo copies it during prebuild. Same for `GoogleService-Info.plist` (project root, copied to `ios/`).

The pre-read hook blocks reading `google-services.json` directly — it contains an API key. Reference `docs/PUSH_NOTIFICATIONS_KT.md` for the setup steps.

## EAS Build

- `eas.json` declares profiles: `development` (with dev client), `preview` (internal), `production` (store).
- New native dependencies require a new EAS build — Metro fast refresh won't pick them up.
- After adding a native module, run `eas build --profile development --platform android` (or ios) and reinstall on the test device.

## Env variables in Expo

- `EXPO_PUBLIC_*` is bundled into the app binary. Use it for non-secret config (API base URL, etc.).
- Anything secret (Supabase service-role key, internal API keys) must NOT have `EXPO_PUBLIC_*` prefix and must NEVER be referenced from app code.
- Server-side secrets stay in Railway env vars, accessed only by the backend.

## Deep links

- Configured in `app.config.ts` under `scheme` and `intentFilters`.
- Validated client-side via `modules/parent/services/notification-deep-link.ts` — extend that allowlist when adding new safe paths. Never `Linking.openURL(arbitrary)` from a notification payload.

## What NOT to do

- ❌ Edit `android/` or `ios/` manually.
- ❌ Add native deps via `npm install <native-pkg>` without a follow-up EAS build.
- ❌ Put secrets behind `EXPO_PUBLIC_*`.
- ❌ Skip the deep-link allowlist when handling a notification tap.
- ❌ Run `expo prebuild --clean` without explicit user confirmation.
